== Overview

Quintauris' machine meta-model formally defines a set of meta-classes describing the structure and properties of machine models employed across the {project}. The present page is a human-readable definition, which is matched with a machine-readable definition in JSON-Schema format.

The top-level machine meta-model is a composition of smaller, more purpose-specific meta-models. The following is a simplified, top-level description of the meta-model hierarchy:

== Identifier

Identifiers conform to the following regular expression: `^[a-zA-Z_]+[0-9a-zA-Z_]*$`

== Number

Numeric values conform to one of the following regular expressions:

Binary value:: `^0b[01]+$`
Hexadecimal value:: `^0x[0-9a-fA-F]+$`
Decimal value:: `^[\+\-]?[0-9]+(\.[0-9]+)?$`

== Evaluated expressions

Attributes marked `Yes` in the `Expression` column are strings that shall be evaluated as numeric expressions by model consumers to produce an integer result (e.g. `4096 * 8` or `4K * 16`).

Supported number formats are:

* Decimal <<_number>>, optionally suffixed as follows:
 * `K` multiply by `1024` (e.g. `4K = 4*1024 = 4096`)
 * `M` multiply by `1048576`
 * `G` multiply by `1073741824`
 * `k` multiply by `1000` (e.g. `4k = 4*1000 = 4000`)
 * `m` multiply by `1000000`
 * `g` multiply by `1000000000`
* Unsigned integer in hexadecimal representation as described in <<_number>>
* Unsigned integer in binary representation as described in <<_number>>

Supported operators are, in order of precedence:

* `()`: parentheses for grouping and precedence
* `+`, `-`: unary plus and minus
* `*`, `/`, `%`: binary multiplication, exact division and modular division
* `+`, `-`: binary addition and subtraction

Supported built-in functions are (both require at least one parameter):

* `min(a, b, ...)`
* `max(a, b, ...)`

Values resulting from expression evaluation, signed or unsigned, must have an integral part representable in 128 bits or less.

Decimal values will be rounded half toward zero.

Undefined operations such as (modular) division by zero and overflow shall stop model parsing and report the error appropriately.

== Declaration

It is possible to declare, either inline or `import` ing them, model elements in the following contexts:

* <<_machine>>: <<_peripheral>>s and <<_addressable>>s
* <<_peripheral>>: <<_addressable>>s
* <<_addressable>>: <<_addressable>>s and <<_register>>s
* <<_register>>: <<_field>>s

 under a user-defined name. For example, the following code brings the model entity defined in `riscv/model/ns16550/model.json` to the current <<_machine>> context, under the name `ns16550`:


----
  "declarations": {
    "ns16550": {
      "import": "riscv/model/ns16550/model.json"
    }
  }
----

Alternatively, `ns16550` can also be declared inline:

----
  "declarations": {
    "ns16550": {
      "peripheral": {
        "name": "uart_ns16550",
        "addressables": {
          ...
        }
      }
    }
  }
----

Now `ns16550`, no matter whether it was imported or declared inline, can be used to produce `ns16550` <<_instance>>s like `uart0` under `peripherals`:

----
  "uart0": {
    "instance_of": "ns16550",
    "peripheral": {
      "base": "0x10000000"
    }
  },
----

`substitutions` can be used to apply custom changes to the imported entity, for example:

----
  "declarations": {
    "ns16550": {
      "import": "riscv/model/ns16550/model.json"
      "substitutions": {"FOO": "BAR"}
    }
  }
----

will replace every occurrence `${FOO}` in `riscv/model/ns16550/model.json` string values with `BAR`.

`substitutions` key/value sets in nested `import`s are merged recursively i.e. deeper keys/values taking precedence over those defined by shallower `import`s.

ctr_decl_003:: `peripheral` can only appear in the context of <<_machine>>
ctr_decl_004:: `addressable` can only appear in the context of <<_machine>>, <<_peripheral>> and <<_addressable>>
ctr_decl_005:: `register` can only appear in the context of <<_addressable>>
ctr_decl_006:: `field` can only appear in the context of <<_register>>

    "peripheral": {
      "base": "0x10000000"
    }

----

== Register

Registers are data instances within <<_addressable>>s. How individual registers are accessed is determined by the register's `class` attribute:

`memory_mapped`:: register is accessed via common fetch/store instructions on the register's address (parent's computed address + `offset` determines the absolute address)
`control_status`:: register is accessed via direct RISC-V's CSR read/write instructions (parent's computed address + `offset` determines the CSR index)

|Reset mask applicable (i.e. on reset `field = (field & ~reset_mask) \| (reset_value & reset_mask)`) to the field for the named <<_reset_type>>

|`write_policy`
|string
|No
|`any`
|One of `preserve` (writes must mirror the last read value), `legal` (writes must hold legal values) or `any` (any value is acceptable). Ignored if enclosing <<_register>> `access_policy` is `read_only`

|`read_policy`
|string
|No
|`any`
|One of `ignore` (read values shall be ignored), `legal` (read values are always legal) or `any` (any value can be read). Ignored if enclosing <<_register>> `access_policy` is `write_only` or `write_only_once`
|===

=== Constraints

ctr_fild_001:: `position` must be an integer number in the range `[-w, w - 1]` where `w` is the value of the `width` attribute from the enclosing <<_register>>
ctr_fild_002:: `length` must be an integer number in the range `[1, w - p]` where `w` is the value of the `width` attribute from the enclosing <<_register>>, and `p` is the normalized position (`position`, or `width + position` when negative)
ctr_fild_003:: <<_value>> keys shall conform to <<_identifier>>
ctr_fild_004:: In `on_read` values `clear`, `set`, `toggle` and `modify` are mutually exclusive
ctr_fild_005:: `on_write` keys shall either conform to unsigned integer <<_number>> (binary, hexadecimal or decimal) or be `any`
ctr_fild_006:: In `on_write` values `clear`, `set`, `toggle` and `modify` are mutually exclusive
ctr_fild_007:: Each element of `ranges` must be a 2-element array of strings that evaluate to integer numbers
ctr_fild_008:: If both `values` and `ranges` are defined, values in `values` must all be contained by `ranges`
ctr_fild_009:: `on_reset/__reset-name__` shall reference a valid <<_reset_type>> defined at <<_machine>> level
ctr_fild_010:: `on_reset/__reset-name__/value` shall be a valid unsigned integer <<_number>> of no more bits than `length` bits
ctr_fild_011:: `on_reset/__reset-name__/mask` shall be a valid unsigned integer <<_number>> of no more bits than `length` bits
ctr_fild_012:: `on_reset/__reset-name__` `value` and `mask` shall be consistent with enclosing <<_register>>'s `on_reset/__reset-name__` `value` and `mask`, if defined
ctr_fild_013:: If `hw_volatile` is `true`, then the parent <<_register>> `hw_volatile` attribute shall be also `true`
ctr_fild_014:: Sets of values defined by `read_values` and `values` shall be disjunct
ctr_fild_015:: Sets of values defined by `write_values` and `values` shall be disjunct
